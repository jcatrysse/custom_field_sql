- Severity: major
  File: app/controllers/custom_sql_search_controller.rb:40-48 (authorize_search)
  Problem: Authorization is too permissive for users with only :edit_own_issues. The action allows access if the user has any of [:add_issues, :edit_issues, :edit_own_issues] on the project, regardless of whether the request is for creating a new issue (issue_id blank) or for an issue they do not own. A user who cannot add issues and cannot edit others’ issues can still call /custom_sql_search/search and retrieve results for that project.
  Scenario: In a public project where Non member has only :edit_own_issues, an outsider logs in and directly calls /custom_sql_search/search?project_id=<public_project_id>&custom_field_id=<visible_field_id>&term=abc without an issue_id. They receive JSON results even though they cannot add issues or edit others’ issues, potentially exposing data the field’s query returns.
  Fix: Tighten the check to the actual context:
  - When issue_id is present: allow if User.current.allowed_to?(:edit_issues, @project) or (User.current.allowed_to?(:edit_own_issues, @project) && @issue.author_id == User.current.id).
  - When issue_id is blank (new issue or bulk edit): require User.current.allowed_to?(:add_issues, @project) or (for bulk edit only) :edit_issues; do not accept :edit_own_issues alone.
  Example:
    allowed = @project.all_issue_custom_fields.include?(@custom_field) &&
              @custom_field.visible_by?(@project, User.current) &&
              (
                (@issue && (User.current.allowed_to?(:edit_issues, @project) ||
                            (User.current.allowed_to?(:edit_own_issues, @project) && @issue.author_id == User.current.id))) ||
                (!@issue && User.current.allowed_to?(:add_issues, @project))
              )
    deny_access unless allowed

  Resolution: fixed in the next commit ("Search: with an issue, require that the user may edit it"), narrower than proposed: with an issue_id the user must be able to edit that issue's attributes (Issue#attributes_editable?, which covers edit_issues and edit_own_issues on one's own issue); without an issue_id (new issue, bulk edit) add_issues, edit_issues or edit_own_issues stays enough, because bulk edit of one's own issues has no issue_id and needs edit_own_issues. Test: test_issue_the_user_cannot_edit_is_refused (fails without the fix); browser: search_authorization reporter-issue-not-editable and manager-edit-issue.

- Severity: major
  File: lib/custom_sql_search_hook.rb:38
  Problem: Parsing form_params into a Hash does not handle blank or whitespace-only lines. Using Hash[field.form_params.to_s.each_line.map { |str| str.split("=", 2) }] will raise when a line lacks an "=" (e.g., a trailing blank line), breaking the issue form rendering.
  Scenario: An administrator saves form_params with a trailing newline and a blank line (or a comment line without "="). Opening a new issue causes the hook to run and raises ArgumentError ("odd number of arguments for Hash" or wrong element type), returning HTTP 500 for the form.
  Fix: Ignore lines without an "=" and trim whitespace. For example:
    lines = field.form_params.to_s.each_line(chomp: true).map(&:strip).reject(&:blank?)
    p = lines.select { |s| s.include?('=') }.to_h { |s| s.split('=', 2) }

  Resolution: does not happen. Measured on Ruby 3.2.6 and 3.3.6: Hash["p0=a\n\n# note\n  \n".each_line.map { |s| s.split("=", 2) }] gives {"p0"=>"a\n", "\n"=>nil, "# note\n"=>nil, "  \n"=>nil}, no exception; the null entries become empty request parameters nobody's SQL uses. The case that did raise (an expression containing "=") is fixed in 0e8ffd0 ("Form params: split each line on the first equals sign only"), with a test. Not changed further, to keep the diff minimal.
