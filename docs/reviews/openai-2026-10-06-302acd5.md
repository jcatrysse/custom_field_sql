Major, lib/custom_sql_search_hook.rb:30-36
Problem: Building the form_params hash with Hash[field.form_params.to_s.each_line.map { |str| str.split("=", 2) }] raises when a line has no "=" (empty line or comment), causing “odd number of arguments for Hash” and a 500 on issue forms.
Scenario: An administrator saves a sql_search field with form parameters that include a trailing blank line or a comment line (for readability). Opening the new issue form renders the hook, which evaluates the code above and crashes with a 500.
Fix: Ignore lines without an "=" and strip newlines before building the hash, e.g.:
pairs = field.form_params.to_s.each_line(chomp: true).filter_map { |s| k,v = s.split('=', 2); (k && v) ? [k, v] : nil }
p = pairs.to_h

Resolution: does not happen (same claim as in openai-2026-10-06-7a45188.md, measured on Ruby 3.2.6 and 3.3.6: a line without "=" becomes a key with a null value, no exception). Now pinned by test_blank_and_comment_lines_in_form_params in the next commit.

Major, lib/custom_sql_search_hook.rb:38-52
Problem: The script tag includes admin-provided values (form_params, strict_error_message) embedded inside a JavaScript string via JSON.parse(<dumped_json>) without guarding against a closing </script> sequence. An admin can inject “</script><script>…” in these fields to break out of the script element and run arbitrary JS in viewers’ browsers (XSS).
Scenario: Administrator sets “Strict error message” to “</script><script>alert(document.cookie)</script>”. Visiting the issue form loads the hook’s inline <script> that contains JSON.parse("... </script><script> ..."), which prematurely closes the tag and executes the injected script as the current user.
Fix: Escape the closing script sequence in the dumped JSON before embedding, for both form_params and options:
dump = obj.to_json.dump.gsub(%r{</}, '<\/')
… JSON.parse(#{dump}) …
Alternatively, avoid embedding JSON in a script string: place data in a <script type="application/json"> node or data-* attributes and read it at runtime; or wrap with Rails escape_javascript/json_escape when building the string.

Resolution: not exploitable as described. Rails' JSON encoding escapes "<" and ">" (ActiveSupport::JSON::Encoding.escape_html_entities_in_json is true; measured on 7.0 and 5.1: {m: "</script>"}.to_json gives "\u003c/script\u003e"), so neither the message nor the form parameters can close the script element; and only an administrator, who already writes the SQL, can set them. Pinned by test_settings_cannot_close_the_script_element in the next commit, so a later change of the encoding would be caught.
