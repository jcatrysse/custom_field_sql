## Part 1 of 1

Major, app/controllers/custom_sql_search_controller.rb:31-44
The search action authorizes based on the given issue OR the given project, but never verifies that the issue passed in params[:issue_id] actually belongs to params[:project_id]. In authorize_search, when @issue is present, allowed is granted if the user can edit that issue, regardless of whether they have add/edit rights in the project identified by project_id. This lets a user who can edit an issue in project A call /custom_sql_search/search with project_id of project B (where they may not be allowed to add/edit issues), and still get results for project B as long as the field is visible in B.
Concrete failure scenario:
- User U is a manager in Project A (can edit issues there), and a non-member in public Project B (no add/edit issues there).
- A sql_search field F is enabled and visible in Project B.
- U crafts a request: /custom_sql_search/search?project_id=<B.id>&issue_id=<id of an issue U can edit in A>&custom_field_id=<F.id>&term=foo
- authorize_search returns true because @issue.attributes_editable?(U) is true for the A issue; visible_by? and all_issue_custom_fields are evaluated against B, which a public project may pass. U receives results for Project B even though U cannot add/edit issues in B, violating the intended rule in README (“Only logged in users who can add or edit issues in the project ... get results.”).
Fix:
- Enforce that a given issue belongs to the given project before authorization, and keep the “may add or edit issues in the project” requirement for both new (no issue) and edit (with issue) cases.
Example patch:
  def find_project_and_issue
    @project = Project.find(params[:project_id])
    @issue = params[:issue_id].blank? || params[:issue_id] == 'null' ? nil : Issue.visible.find(params[:issue_id])
    if @issue && @issue.project_id != @project.id
      render_404 and return
    end
  rescue ActiveRecord::RecordNotFound
    render_404
  end

  def authorize_search
    allowed = @project.all_issue_custom_fields.include?(@custom_field) &&
              @custom_field.visible_by?(@project, User.current) &&
              if @issue
                @issue.project_id == @project.id && @issue.attributes_editable?(User.current) &&
                  [:add_issues, :edit_issues, :edit_own_issues].any? { |p| User.current.allowed_to?(p, @project) }
              else
                [:add_issues, :edit_issues, :edit_own_issues].any? { |p| User.current.allowed_to?(p, @project) }
              end
    deny_access unless allowed
  end

Resolution: fixed in the next commit ("Search: an editable issue does not open another project"), without the proposed "issue must be in the given project" check: on the edit form the project select can move the issue, and the form then asks with the target project and the issue's id, which that check would refuse. Instead the project rule (add_issues, edit_issues or edit_own_issues in the given project) now always applies, and the issue rule (may edit that issue) comes on top.
