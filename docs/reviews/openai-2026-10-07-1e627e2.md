Major, app/controllers/custom_sql_search_controller.rb:74-82
Missing visibility check for UserCustomField in search authorization allows suggestion queries on hidden user fields by any logged-in user when the field is editable. The UserCustomField branch authorizes with user.admin? || (user.logged? && @custom_field.editable?) and does not verify that the field is visible to the requester. Failure scenario: Create a User custom field with field_format 'sql_search', visible: false (or otherwise hidden from normal users), editable: true, whose SQL returns sensitive data (e.g., user logins). A non-admin logged-in user can call /custom_sql_search/search?custom_field_id=<id>&term=... and receive results even though the field is not visible on “My account” for them. Fix: also require field visibility for non-admins, e.g.:
when UserCustomField
  user.admin? || (user.logged? && @custom_field.editable? && (@custom_field.visible? || @custom_field.visible_by?(nil, user)))
and add a functional test that a hidden user field (visible: false) returns 403 for a non-admin even if editable: true.

Resolution: not changed, repeats finding 1 of openai-2026-10-07-43065bd.md. The premise is wrong: core's My account lists every editable user field whatever `visible` says (app/views/my/account.html.erb:50, `@user.custom_field_values.select(&:editable?)`), so a non-visible editable field IS on My account and its owner may fill it in; `visible` only controls whether others see the value.
