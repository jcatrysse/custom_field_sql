Major, app/controllers/custom_sql_search_controller.rb:83-102
User custom fields bypass field visibility. In search_allowed?, the UserCustomField branch allows any logged-in user to use the search when the field is editable, without checking that the field is visible to the user. Failure scenario: Create a UserCustomField with field_format 'sql_search', editable: true, visible: false, role_ids excluding the Reporter role. As a Reporter, call GET /custom_sql_search/search?custom_field_id=<id>&term=adm (XHR). The action returns 200 and the SQL runs with full DB visibility, even though the field is hidden for the role. Fix: include a visibility check for user fields, same as for other types, e.g.:
- when UserCustomField: @custom_field.visible_by?(nil, user) && (user.admin? || (user.logged? && @custom_field.editable?))

Resolution: not changed. A user custom field has no role visibility in Redmine (UserCustomField does not override `visible_by?`, its form has no roles), and core's My account page offers every *editable* user field to its owner whatever `visible` says (`@user.custom_field_values.select(&:editable?)`, app/views/my/account.html.erb). `visible` only governs whether others see the value on the profile. Requiring it would refuse suggestions on a field the user may fill in, so the check follows core: administrators, or the logged in owner of an editable field. The query's own reach is documented in the README.

Major, app/controllers/custom_sql_search_controller.rb:88-95
Wrong permission for project fields when a project_id is provided; and meaningless global check for :add_subprojects. The ProjectCustomField branch requires :edit_project when @project is present. On the new subproject form, a script may pass the parent project_id for scoping; a user who is allowed to add subprojects but not edit the parent project is incorrectly refused (403). Additionally, when no @project is present, user.allowed_to_globally?(:add_subprojects) is not a valid check (add_subprojects is a project-scoped permission). Failure scenario: User has :add_subprojects on project X but not :edit_project. A view_customize script wires the field and sends project_id=X on /projects/new?parent_id=X. GET /custom_sql_search/search?custom_field_id=<id>&project_id=X&term=e2e returns 403, although the user may create a subproject. Fix:
- Allow :add_subprojects when @project is present:
  when ProjectCustomField
    @custom_field.visible_by?(@project, user) &&
      (@project ? (user.allowed_to?(:edit_project, @project) || user.allowed_to?(:add_subprojects, @project))
                : user.allowed_to_globally?(:add_project))
- Drop user.allowed_to_globally?(:add_subprojects) entirely (it will never be true).

Resolution: partly accepted, fixed in ac6586a with a test that fails without it (test_project_field_needs_edit_project: 403 before, 200 after): with a project id, `add_subprojects` in that project is enough too. The global `add_subprojects` check stays: core authorizes projects#new with `authorize_global`, and both `add_project` and `add_subprojects` map to it (lib/redmine/preparation.rb), so `allowed_to_globally?(:add_subprojects)` is true for a member with that permission anywhere, exactly as core lets that user open the new project form.
